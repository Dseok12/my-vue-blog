# Stage 8 — 어떤 프로젝트든 만드는 법

> 전체 로드맵: [README](README.md) · 이전: [07 Vue 심화](07-vue-advanced.md)

## 목표

지금까지는 **이미 설계된 프로젝트**를 따라 만들었다. 이제 **처음 보는 요구사항**을 받았을 때
빈 폴더에서 시작해 배포까지 가는 **공정**을 익힌다.

> 초보와 숙련자의 차이는 "아는 문법의 양" 이 아니다.
> **코드를 쓰기 전에 무엇을 결정하고, 어떤 순서로 만드는가** 의 차이다.

---

## 8-1. 9단계 공정

```
 ① 요구사항   무엇을 만드나 (한 문장 → 기능 목록 → 우선순위)
 ② 화면       어떤 화면이 있고, 화면 사이를 어떻게 이동하나
 ③ 데이터     무엇을 저장하나 (테이블, 관계)
 ④ API        화면이 서버에 무엇을 요청하나 (주소, 요청, 응답, 권한)
 ⑤ 컴포넌트   화면을 어떤 부품으로 나누나 (트리, 스토어)
 ⑥ 구현 순서  무엇부터 만드나 (얇게, 끝까지)
 ⑦ 구현       만든다 (작게 만들고 바로 확인)
 ⑧ 검증       테스트, 반응형, 접근성, 오류 상황
 ⑨ 배포·회고  올리고, 배운 것을 적는다
```

**①~⑥ 은 코드를 한 줄도 쓰지 않는다.** 종이, 메모장, `docs/` 폴더의 마크다운으로 한다.
여기에 전체 시간의 20~30% 를 쓰면, 나머지 70% 가 훨씬 빨라진다.

아래에서 각 단계를 **이 다이어리 프로젝트를 거꾸로 분석**하며 배우고,
그다음 **새 프로젝트(가계부)** 에 똑같이 적용한다.

## 8-2. ① 요구사항 — 무엇을 만드나

### 한 문장으로

```
"회원마다 자기만 보는 일기·독서기록·감정기록을 쓰고, 원하면 공개해서 댓글과 좋아요를 받는 다이어리"
```

한 문장으로 못 쓰면 아직 무엇을 만들지 모르는 것이다.

### 사용자 이야기 (User Story)

```
[누가]    [무엇을 하고 싶다]                    [왜]
회원은    오늘 날짜로 일기를 쓰고 싶다            하루를 기록하려고
회원은    캘린더에서 날짜를 눌러 그날 글을 보고 싶다  지난 기록을 찾으려고
회원은    글을 공개로 바꾸고 싶다                 다른 사람과 나누려고
다른 회원은 공개 글에 댓글을 달고 싶다            공감을 전하려고
비회원은   첫 화면에서 로그인하고 싶다
```

### 우선순위 — MoSCoW

| 등급 | 뜻 | 다이어리의 예 |
| --- | --- | --- |
| **Must** | 없으면 앱이 아니다 | 가입/로그인, 글 CRUD, 내 글만 보기 |
| **Should** | 있어야 쓸 만하다 | 캘린더, 공개/비공개, 이미지 |
| **Could** | 있으면 좋다 | 좋아요, 대댓글, 검색 |
| **Won't (이번엔)** | 다음 버전 | 알림, 친구, 다크 모드 |

**첫 버전(MVP)은 Must 만 만든다.** 완성한 뒤 Should 를 하나씩 붙인다.
처음부터 다 만들려다 아무것도 끝내지 못하는 것이 가장 흔한 실패다.

### 규칙(비즈니스 규칙)을 문장으로 뽑아낸다

요구사항에 숨어 있는 규칙을 **번호를 붙여** 적는다. 나중에 이것이 검증 코드와 테스트가 된다.

```
R1. 비공개 글은 작성자만 읽을 수 있다                 → diaryService.assertReadable
R2. 수정·삭제는 작성자만 할 수 있다                   → diaryService.assertOwner
R3. 좋아요·댓글은 공개 글에만 가능하다                 → diaryService.assertPublic
R4. 대댓글은 1단계까지 (답글의 답글은 같은 단계로)       → commentService.create
R5. 날짜는 한국 시간 기준                            → utils/date.js 의 TIME_ZONE
R6. 이미지는 10MB 이하, jpg/jpeg/png/gif/webp, 5장까지 → config.js, middlewares/upload.js
R7. 캘린더 첫 요일은 일요일                          → buildMonthMatrix
```

[CLAUDE.md](../CLAUDE.md) 의 "수행되어야 할 리스트" 가 바로 이 단계의 결과물이다.

## 8-4. ③ 데이터 — 무엇을 저장하나

### 명사를 찾는다

요구사항 문장에서 **명사**에 밑줄을 긋는다: 회원, 다이어리(글), 이미지, 댓글, 좋아요.
명사가 테이블 후보, 그 명사를 설명하는 말이 컬럼 후보다.

### 관계를 정한다

```
users 1 ───< N diaries          회원 한 명이 글 여러 개
diaries 1 ───< N diary_images   글 하나에 이미지 여러 장
diaries 1 ───< N comments       글 하나에 댓글 여러 개
comments 1 ───< N comments      댓글 하나에 답글 여러 개 (자기 참조)
users N >───< N diaries         좋아요: 회원과 글의 다대다 → 중간 테이블 diary_likes
     (diary_likes)
```

### ERD (표로 그리기)

```
users                    diaries                       comments
┌──────────────┐        ┌─────────────────┐          ┌─────────────────┐
│ id        PK │◄──┐    │ id           PK │◄──┐      │ id           PK │◄─┐
│ email     UQ │   └────│ user_id      FK │   ├──────│ diary_id     FK │  │
│ password_hash│        │ title           │   │      │ parent_id    FK │──┘
│ nickname  UQ │        │ content         │   │      │ user_id      FK │
│ created_at   │        │ category  ENUM  │   │      │ content         │
└──────────────┘        │ mood            │   │      │ created_at      │
                        │ date_key  (KST) │   │      └─────────────────┘
                        │ visibility ENUM │   │
                        │ created_at      │   │      diary_likes
                        │ updated_at      │   │      ┌─────────────────┐
                        └─────────────────┘   ├──────│ diary_id  PK,FK │
                                              │      │ user_id   PK,FK │
                                              │      └─────────────────┘
                                              │      diary_images
                                              └──────│ diary_id     FK │
                                                     │ url, name, sort │
```

**설계 질문 체크리스트**

- [ ] 각 테이블에 `id`, `created_at` 이 있는가
- [ ] 중복되면 안 되는 값에 UNIQUE 가 있는가 (이메일, 닉네임, 좋아요 한 번)
- [ ] 부모가 지워지면 자식은 어떻게 되나 (`ON DELETE CASCADE`)
- [ ] 자주 검색하는 조건에 인덱스가 있는가 (`user_id + date_key`)
- [ ] **계산할 수 있는 값을 저장하고 있지는 않은가** — 좋아요 수는 저장하지 않고 센다
- [ ] 시간대는? (시각은 UTC, 날짜 키는 KST 문자열 — [schema.sql](../backend/src/db/schema.sql) 맨 위 주석)

## 8-5. ④ API — 화면과 서버의 약속

**화면 목록을 보면서** "이 화면을 그리려면 무엇이 필요한가" 를 하나씩 적는다.

| 화면 | 필요한 데이터 / 동작 | API |
| --- | --- | --- |
| 내 다이어리 | 내 글 목록 (필터, 페이지) | `GET /diaries?category&keyword&cursor&limit` |
| 캘린더 | 이번 달 날짜별 개수 | `GET /diaries/monthly-counts?year&month` |
| 상세 | 글 하나 | `GET /diaries/:id` |
| 상세 | 좋아요 토글 | `POST /diaries/:id/like` |
| 상세 | 댓글 목록 / 작성 / 삭제 | `GET·POST /diaries/:id/comments`, `DELETE .../:cid` |
| 작성 | 이미지 올리기 → 저장 | `POST /uploads/image` → `POST /diaries` |

**각 API 마다 다섯 가지를 정한다**

```
POST /api/diaries/:id/comments
  인증   : 필요 (Bearer 토큰)
  요청   : { content: string(1~1000자), parentId?: string }
  응답   : 201 { comment: Comment }
  오류   : 400 비공개 글 / 내용 없음,  401 토큰 없음,  404 글·원본 댓글 없음
  규칙   : R3, R4
```

**응답 모양을 통일한다** — 이 프로젝트의 규칙

```
성공: 단건 { diary }, 목록 { items, nextCursor, total }, 동작 { liked, likeCount }
실패: 항상 { message } + 알맞은 상태 코드
id 는 문자열, 시각은 ISO 문자열, 날짜는 'YYYY-MM-DD'
```

이렇게 정해 두면 프론트엔드의 [api/index.js](../frontend/src/api/index.js) 주석과
백엔드의 [backend/README.md](../backend/README.md) 표가 **같은 문서** 가 된다.
그리고 **mock API 를 먼저 만들어** 백엔드 없이 화면을 끝까지 만들 수 있다.

### 상태를 어디에 둘지 표로 정한다

| 상태 | 위치 | 이유 |
| --- | --- | --- |

| 모달 열림 | 컴포넌트 `ref` | 그 화면에서만 |
| 사이드바, 토스트 | `ui` 스토어 | 레이아웃 전체 |

## 8-7. ⑥ 구현 순서 — 얇게, 끝까지

**나쁜 순서**: 모든 화면의 CSS → 모든 컴포넌트 → 모든 API → 연결 (마지막에 다 안 맞는다)

**좋은 순서**: **기능 하나를 화면부터 DB 까지 얇게 관통**시키고, 하나씩 늘린다.

```
1주차  뼈대     Vite + 라우터 + 레이아웃 + Base 컴포넌트 + mock API + 로그인(mock)
2주차  핵심 1   글 목록 → 작성 → 상세 → 수정 → 삭제  (mock 으로 끝까지)
3주차  백엔드   Express + DB + 인증 → 글 CRUD API → VITE_USE_MOCK=false 로 연결
4주차  Should   캘린더 → 공개/비공개 → 이미지 업로드
5주차  Could    좋아요 → 댓글/대댓글 → 검색 → 더 보기
6주차  마감     빈 화면·오류·로딩 점검 → 모바일 → 접근성 → 테스트 → 배포
```

**매일 끝날 때 "동작하는 상태" 로 커밋한다.** 반쯤 만든 기능은 브랜치에 둔다.

## 8-8. ⑦ 구현할 때의 습관

1. **작게 쓰고 바로 확인한다** — 10줄 쓰고 저장하고 화면/콘솔을 본다. 100줄 쓰고 확인하면 오류가 어디서 났는지 모른다
2. **하드코딩으로 먼저 보이게 한다** — API 연결 전에 `const items = [{...}, {...}]` 로 화면부터 완성
3. **복사하고 싶어지면 멈춘다** — 세 번째 복사 전에 함수/컴포넌트로 뺀다
4. **이름을 고민한다** — 이름이 안 떠오르면 그 함수가 두 가지 일을 하고 있다는 신호다
5. **커밋은 작게** — "기능 하나 / 버그 하나" 마다

### 디버깅 공정 — 막혔을 때 순서대로

```
1. 재현     항상 같은 방법으로 버그를 일으킬 수 있는가? (못 하면 조건부터 찾는다)
2. 위치     어느 층의 문제인가?
             화면 표시? → Vue Devtools 로 컴포넌트/스토어 값 확인
             요청?     → Network 탭: 요청을 보냈나, 무엇이 왔나
             서버?     → 백엔드 터미널의 로그 / 오류
             DB?       → SQL 을 직접 실행해 본다
3. 가설     "필터가 비어서 전체가 오는 것 같다" — 하나만 세운다
4. 확인     console.log / 중단점(debugger) 으로 가설을 확인한다
5. 수정     원인을 고친다 (증상을 덮지 않는다)
6. 고정     같은 버그가 다시 나지 않게 테스트를 추가한다
```

> **Vue Devtools** (브라우저 확장) 를 반드시 설치한다. 컴포넌트의 props, 스토어의 상태,
> 라우터의 현재 경로를 실시간으로 보고 고칠 수 있다.

### 처음 보는 라이브러리를 도입하는 법

1. 공식 문서의 **Getting Started / Quick Start** 를 처음부터 끝까지 따라 한다 (내 프로젝트가 아니라 빈 프로젝트에서)
2. 내가 쓸 기능 **하나**만 내 프로젝트에 붙인다
3. 공식 예제와 내 코드가 다르면, 다른 부분을 하나씩 공식 예제 쪽으로 맞춰 본다
4. 버전을 확인한다 — 검색 결과의 블로그 글은 옛 버전일 때가 많다. **공식 문서가 기준**이다

## 8-11. 적용 연습 — 가계부 앱을 처음부터 설계하기

같은 9단계를 새 주제에 적용한다. **아래를 읽기 전에 먼저 스스로 ①~⑤ 를 써 보고**, 비교한다.

### ① 요구사항

```
한 문장: "회원이 수입·지출을 기록하고, 월별로 카테고리별 합계와 예산 대비 사용량을 보는 가계부"

Must   가입/로그인, 거래 CRUD (날짜, 금액, 수입/지출, 카테고리, 메모), 월별 목록, 월 합계
Should 카테고리 관리, 월 예산 설정과 진행률, 카테고리별 원형 그래프
Could  검색, CSV 내보내기, 반복 거래(매달 월세)
Won't  가족 공유, 은행 연동

규칙
R1. 금액은 1원 이상의 정수 (원 단위, 소수점 없음)
R2. 내 거래와 내 카테고리만 보이고 고칠 수 있다
R3. 거래가 있는 카테고리는 지울 수 없다 (또는 '미분류' 로 옮긴다 — 정책을 정한다)
R4. 날짜와 월 경계는 KST 기준
R5. 월 합계 = 그 달 수입 합 - 지출 합
```

### ② 화면

| 화면 | 주소 | 내용 |
| --- | --- | --- |
| 로그인/가입 | `/login`, `/signup` | (다이어리 재사용) |
| 월별 대시보드 | `/?month=2026-08` | 이번 달 수입/지출/잔액 카드, 예산 진행률, 원형 그래프, 최근 거래 5개 |
| 거래 목록 | `/transactions?month&type&category` | 날짜별로 묶인 목록, 필터, 더 보기 |
| 거래 작성/수정 | `/transactions/new`, `/transactions/:id/edit` | 폼 |
| 카테고리 | `/categories` | 목록, 추가, 이름 변경, 삭제 |
| 설정 | `/settings` | 월 예산 |

### ③ 데이터

```
users (다이어리와 같음)

categories                      transactions                     budgets
┌──────────────────┐           ┌──────────────────────┐         ┌──────────────────┐
│ id            PK │◄──┐       │ id                PK │         │ id            PK │
│ user_id       FK │   └───────│ category_id       FK │         │ user_id       FK │
│ name             │           │ user_id           FK │         │ month   'YYYY-MM'│
│ type ENUM(in,out)│           │ type  ENUM(in,out)   │         │ amount    INT    │
│ UNIQUE(user,name)│           │ amount   INT UNSIGNED│         │ UNIQUE(user,month)│
└──────────────────┘           │ date_key  'YYYY-MM-DD'│        └──────────────────┘
                               │ memo                 │
                               │ created_at           │
                               │ INDEX(user_id, date_key)│
                               └──────────────────────┘
```

**설계 결정 기록** (나중의 나를 위해 이유를 남긴다)

- 금액은 `DECIMAL` 이 아니라 `INT` — 원화는 소수점이 없다. **돈을 `FLOAT` 로 저장하면 안 된다** (0.1 + 0.2 ≠ 0.3)
- 월 합계는 저장하지 않고 `SUM()` 으로 센다 — 거래를 고칠 때마다 합계를 맞출 필요가 없다
- `date_key` 를 다이어리처럼 KST 문자열로 — 월별 조회가 `LIKE '2026-08%'` 로 끝난다

### ④ API

```
GET    /api/summary?month=2026-08
       → { income, expense, balance, budget, byCategory: [{ categoryId, name, total }] }
GET    /api/transactions?month&type&categoryId&cursor&limit → { items, nextCursor, total }
POST   /api/transactions        { type, amount, categoryId, dateKey, memo } → 201 { transaction }
PUT    /api/transactions/:id    → { transaction }          (본인만, R2)
DELETE /api/transactions/:id    → {}                       (본인만, R2)
GET    /api/categories          → { items }
POST   /api/categories          { name, type } → 201        (같은 이름 409)
DELETE /api/categories/:id      → {}                       (거래가 있으면 409, R3)
PUT    /api/budgets/2026-08     { amount } → { budget }
```

### ⑤ 컴포넌트와 상태

```
DashboardView
├─ MonthPicker          ← 주소의 ?month 를 v-model 로 (다이어리 AppSidebar 의 selectedDate 기법)
├─ SummaryCard × 3      (수입 / 지출 / 잔액)
├─ BudgetProgress       (예산 대비 %, 80% 넘으면 경고색)
├─ CategoryChart        (vue-chartjs, defineAsyncComponent 로 지연 로딩)
└─ TransactionItem × 5

TransactionListView
├─ TransactionFilterBar
├─ (날짜별 그룹) DayGroup × N  → computed 로 items 를 dateKey 별로 묶는다
│   └─ TransactionItem × N
└─ LoadMoreButton       ← 다이어리에서 그대로 가져온다

재사용: BaseButton, BaseInput, BaseModal, EmptyState, LoadingBlock, AppToast,

```

```
스토어
```

## 8-12. 프로젝트 사다리 — 10단계

한 칸 오를 때마다 **새 기술 하나**가 추가된다. 각 프로젝트를 9단계 공정으로 만든다.
**한 칸을 끝내야 다음 칸으로 간다.** 끝냈다 = 8-9 검증 표 통과 + 배포 + README.

| # | 프로젝트 | 새로 배우는 것 | 백엔드 | 기간 |
| --- | --- | --- | --- | --- |
| 1 | **할 일 + 메모** | Vue 기본기, localStorage, 컴포넌트 분리 | 없음 | 1주 |
| 2 | **날씨 대시보드** | 외부 공개 API, 로딩/오류 상태, 환경 변수 | 없음 | 1주 |
| 3 | **영화·책 검색** | 라우터(목록/상세), 주소 query 로 검색어 유지, 디바운스, 무한 스크롤 | 없음 | 2주 |
| 4 | **가계부** (8-11) | 첫 풀스택, 집계 SQL(SUM/GROUP BY), 차트 | Express + MySQL | 4주 |
| 5 | **칸반 보드** | 드래그 앤 드롭, 순서 저장(sort_order), 낙관적 업데이트 | 있음 | 3주 |
| 6 | **이 다이어리** | 인증·권한·공개 범위, 댓글 트리, 업로드, 페이지네이션 | 있음 | 6주 |
| 7 | **작은 쇼핑몰** | 관리자/일반 역할, 장바구니, 주문 트랜잭션, 재고 동시성 | 있음 | 6주 |
| 8 | **실시간 채팅** | WebSocket, 읽음 표시, 온라인 상태, 재연결 | Socket.IO | 4주 |
| 9 | **예약 시스템** | 시간 겹침 검사, 중복 예약 방지(락/유니크), 알림 메일, 결제 연동(테스트 모드) | 있음 | 6주 |
| 10 | **나만의 서비스** | 실제 사용자 10명 받기 — 피드백, 로그, 오류 추적, 개선 반복 | 자유 | 계속 |

### 각 프로젝트의 "핵심 난관" 힌트

- **3 검색**: 검색어를 `ref` 가 아니라 주소의 `?q=` 에 두면 뒤로 가기·공유·새로고침이 저절로 된다
- **5 칸반**: 카드를 옮길 때마다 전체 순서를 저장하지 말고, 옮긴 카드의 `sort_order` 만 앞뒤 값의 중간값으로
- **7 쇼핑몰**: "재고 1개 남은 상품을 두 명이 동시에 주문" — `UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0` 의 영향받은 행 수로 판단, 주문 생성과 함께 트랜잭션
- **7 쇼핑몰**: 가격은 **주문 시점의 가격을 주문 테이블에 복사**해 둔다 (상품 가격이 나중에 바뀌어도 주문 내역은 그대로)
- **8 채팅**: 메시지를 DB 에 먼저 저장하고, 저장된 id 를 가진 메시지를 방송한다 (재연결 시 "마지막 id 이후" 를 다시 받는다 — 커서 페이지네이션과 같은 원리)
- **9 예약**: 겹침 조건은 `새 시작 < 기존 끝 AND 새 끝 > 기존 시작` 하나로 끝난다
- **10**: 오류 추적 도구(Sentry 류)를 붙이고, 사용자가 실제로 어디서 막히는지 본다
